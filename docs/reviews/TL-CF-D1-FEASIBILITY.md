## 9. Prisma/D1 compatibility

The current schema/provider and `@prisma/adapter-pg` cannot target D1 unchanged. The D1 path requires SQLite schema mapping and `@prisma/adapter-d1`; the official Prisma D1 guidance currently documents D1 support as Preview and states that transactions are not currently supported by the adapter. This is not a reason to weaken semantics. The implementation must either use a supported direct D1 binding/batch path for atomic multi-write operations or prove an equivalent supported abstraction before migration. Prisma migration generation and local/remote D1 migration workflows must be rebuilt and tested separately.

## 10. Order/idempotency/event semantics

The current order service uses transactions for creation, public intent deduplication, status transition, event creation and publication. `clientReference` is nullable and unique; the service pre-reads and handles concurrent unique conflicts. Transitions use a conditional update on the current status and append one `OrderEvent`; readers replay events by ascending `sequence`.

D1 can provide atomic sequential `batch()` execution with rollback on failure, but the current Prisma D1 adapter cannot supply the existing `$transaction` semantics. The next implementation contract must make the atomic unit explicit: validate/read, conditional write, event append, and required side effects must be one D1 atomic batch or a provably equivalent protocol. `OrderEvent.sequence` must remain a deterministic cursor. SQLite INTEGER is 64-bit, but the exact Prisma/JavaScript representation and concurrent allocation behavior must be tested; no casual conversion to `number` is accepted. Gaps are acceptable only if current consumers rely on ordering, not gaplessness; this must be confirmed by tests.

The PostgreSQL LISTEN/NOTIFY path is not portable to D1. Persisted history and replay are preservable; live admin streaming requires an explicit bounded adaptation and cannot be silently removed.

## 11. Auth/session compatibility

Persistent sessions are relational rows with unique token hashes, expiry and user cascading delete. D1 can preserve this model. Acceptance requires login, lookup, expiry, logout invalidation, inactive-user behavior, normalized email lookup, and concurrent session behavior on the Worker runtime. The current module-level rate-limit map is a separate Worker runtime concern and must not be treated as D1 durability.

## 12. Media/R2/Images compatibility

`Product.imageKey` remains a database-to-object-key relationship. R2 worker storage and Images validation/transformation are independent of PostgreSQL and remain compatible in principle. Replacement/deletion ordering and failure behavior require local R2 emulation or bounded integration tests. Images stays conditional: keep it only for the existing materially useful transformation/validation path and do not add transformations as a feature.

## 14. Components KEEP / REMOVE / DEFER

- KEEP: Workers/vinext, D1 as the candidate transactional store, R2 for persisted media, Images only where the current pipeline materially benefits.
- REMOVE after successful D1 migration: Hyperdrive, external PostgreSQL, PostgreSQL adapter path, and KV if the cache/runtime path can be replaced or disabled without product loss.
- DEFER: Durable Objects, realtime infrastructure redesign, queues, Redis, microservices, Kubernetes and other future infrastructure. The current PostgreSQL LISTEN/NOTIFY SSE path requires an explicit adaptation before full behavior parity, but that adaptation is not designed in this feasibility block.

3. Implement an explicit atomic D1 repository path for order creation, idempotency, status transition and event append.

5. Replace PostgreSQL LISTEN/NOTIFY dependence without silently removing admin event behavior.

## 16. Architecture blockers

No fundamental D1 storage blocker was demonstrated. The following are material implementation gates, not permissions to weaken semantics:

- Prisma D1 transaction limitation: must be resolved by a direct atomic D1 path or equivalent proof.
- PostgreSQL LISTEN/NOTIFY is incompatible: admin live-event behavior needs an explicit adaptation.
- Sequence/number concurrency and exact Prisma representation are not yet proven.
- Account-specific free-tier/billing and resource availability are unknown and remain remote gates.

If the local proof cannot preserve the first two invariants, the recommendation must be revised to `REWORK` or `HUMAN_GATE` before migration.

## 17. Local validation plan

1. Create a disposable local D1 database and SQLite-compatible schema without touching production or applying a remote migration.
2. Run model round-trip tests for all listed models, FK actions, JSON, dates, uniqueness, indexes and enum boundary validation.
3. Exercise order create, public intent retry/concurrent duplicate, transition race, failure injection, event append, cursor replay and sequence ordering through the atomic D1 path.
4. Exercise login, persistent session lookup/expiry/logout and admin authorization.
5. Exercise catalog/settings/media relationships with local R2-compatible fixtures.
6. Run Worker/vinext build, typecheck, lint and full regression suite.
7. Record `LOCAL_INTEGRATION_PASS` only after all required behavior is proven; then prepare a separate remote bounded-validation contract.

## 18. Migration risks

Primary risks are partial writes caused by the Prisma adapter limitation, changed sequence semantics, lost live-event behavior, enum/JSON/date representation drift, SQLite query differences, D1 daily read/write exhaustion, single-threaded/overloaded database behavior, and accidental billing activation. These risks are bounded by local proof gates and explicit Human Gates; they are not resolved by this review alone.
